# 포인트 시스템 (인게임 재화) 계획

작성 2026-10-30 · 상태: 설계, 수치·카탈로그 결정 대기

## 목표
- 1차: 인게임 포인트를 쌓아 **코트 꾸미기 아이템**을 구매·장착한다.
- 장기: 카드 수집형 전환 시 같은 원장·아이템 구조를 그대로 확장한다.

## 설계 원칙
1. **원장(append-only)이 진실** — 잔액은 캐시. 지급·차감은 전부 원장 행으로 남는다.
2. **지급은 서버 전용** — 클라이언트는 포인트를 올릴 수 없다. 차감(구매)만 유저 RPC.
3. **멱등** — 모든 지급은 `idempotency_key`(예: `season:{league}:{season}:{user}:playoff`)로 중복 지급 방지.
4. 아이템은 `item_type`·`rarity`·`quantity`를 처음부터 둔다(코스메틱은 qty 1 고정, 카드 전환 시 그대로 사용).

## 데이터 모델
```
user_wallets   (user_id PK, balance int CHECK >= 0, lifetime_earned int, updated_at)
point_ledger   (id, user_id, delta int, source text, ref_type, ref_id, idempotency_key UNIQUE,
                balance_after int, meta jsonb, created_at)          -- 본인 SELECT만, 쓰기 불가
shop_items     (id text PK, item_type 'court_floor'|'court_palette'|'center_logo_frame'|..., name,
                price int, rarity text, data jsonb, is_active, sort)  -- 읽기전용 메타(카탈로그)
user_items     (user_id, item_id, quantity int default 1, acquired_at, source, PK(user_id,item_id))
achievement_defs / user_achievements                                 -- P4
```
- 장착: `league_teams.court_loadout jsonb` (`{floor, palette, logoFrame ...}`) 1컬럼. 기존 `court_*` 색 컬럼은 그대로 두고, 저장 RPC에서 소유 검증만 추가.

## RPC / 서버
- `grant_points(user, amount, source, idempotency_key, ref_type, ref_id, meta)` — SECURITY DEFINER, **service role만 실행**(authenticated·anon 권한 회수). 지갑 행 잠금 → 원장 insert → 잔액 갱신.
- `purchase_item(p_user_id, p_item_id)` — `assert_caller_is`(10-19 규칙) 사용. 잔액 확인 → 원장(−) → `user_items` 추가 → 한 트랜잭션.
- `update_team_profile` — 장착하려는 아이템/색이 무료 목록이거나 `user_items`에 있는지 검증.
- `admin_grant_points(user, amount, note)` / `admin_grant_points_all(amount, note)` — 전역 어드민 전용, 메모 필수, 원장 `source='admin'`. 전체 회수는 각자 잔액까지만 차감(2026-11-08 구현).

## 수입 구조 (2026-10-30 재설계)
상품 구매 대상은 미정 → 수입 구조부터 확정한다. **우선순위: ② 시즌 마일스톤 > ③ 도전 과제 > ① 일일 정산.**
금액은 상점 가격이 없으므로 **상대 비율**로만 잡았다(아래 수치는 잠정, 가격 확정 후 일괄 스케일).

### 공통 원칙
- **지급 앵커 = "달성 기록 테이블"의 PK.** 달성 행을 `ON CONFLICT DO NOTHING`으로 넣고, 실제로 들어갔을 때만 같은 트랜잭션에서 원장에 지급한다. 재실행·재시도·동시 실행에도 중복 지급이 불가능하다.
- **정의는 코드 상수**(`server/src/shared/points/`의 순수 모듈) — 조건·보상·이름을 한 파일에 둔다. 클라이언트 표시용은 미러. DB 정의 테이블은 만들지 않는다(어차피 지표 계산이 코드라 얻는 게 적음). 지급 당시의 `reward`는 달성 행·원장 `meta`에 스냅샷해서, 나중에 수치를 바꿔도 과거 기록이 안 변한다.
- **공개된 경기만 센다.** 결과 공개 시각(`game_reveal_at`, 연장 포함) 이전 경기를 정산하면 포인트 증가로 스포일러가 된다. 구현 시 공개 판정 함수 재사용(위치 확인 필요).
- **내가 그 팀을 맡은 이후의 경기만 센다.** 시즌 중 팀을 넘겨받은 유저가 이전 유저의 승수로 마일스톤을 받으면 안 된다. 기준은 `room_members.joined_at` 이후 경기. AI 대행 기간도 제외.
- **대상은 `main_league`만**(현재 3개, 그 외 0개). 테스트·토너먼트는 제외, AI 팀(user_id null) 제외.
- **평가 시점**: 가상 하루의 경기가 전부 공개된 뒤 리그 단위로 1회 정산(①+②), 시즌 종료 아카이브(`archiveLeagueSeason` 훅)에서 시즌 종료형 마일스톤·커리어 업적 정산. 같은 평가기를 어디서 불러도 결과가 같게 한다.

### ② 시즌 마일스톤 — 시즌당 1회, 등급제 (2026-10-30 설계)
- **시즌 단위로 리셋된다.** 달성 기록 PK에 `season_number`가 들어 있어서 새 시즌이 시작되면 같은 마일스톤을 다시 받을 수 있다. 별도 리셋 작업은 없다(지표는 그 시즌 `games`에서 새로 계산).
- 한 시즌에 마일스톤 하나는 **최대 1회** 지급. 같은 묶음(승수·연승)의 단계는 서로 다른 마일스톤이라 각각 1회씩 지급된다.
- 달성 기록: `user_season_milestones (league_id, season_number, user_id, milestone_id, rarity, reward, reached_at, ref jsonb)`, **PK = (league_id, season_number, user_id, milestone_id)**.
- 등급 어휘 `Rarity = 'common' | 'rare' | 'unique' | 'epic'`은 **카드·상점 아이템과 공유하는 단일 타입**으로 둔다(`shop_items.rarity`와 동일). 후속 등급(레전더리 등)은 나중에 추가.

#### 설계 방식: "묶음(family) × 단계(step)"
- 마일스톤은 **묶음**(승수, 연승, 원정승, …)마다 지표 하나를 정하고, 그 지표에 **임계값 사다리**를 건다. 단계마다 등급과 보상이 따로 있고 id는 `{묶음}_{임계값}` (`wins_60`, `streak_10`).
- 지표가 임계값에 도달하는 순간 그 단계가 달성된다. 평가 시점에 이미 여러 단계를 넘어 있으면(예: 정규시즌 종료 시 평가하는 묶음) 넘은 단계를 전부 한꺼번에 지급한다.
- 정의는 `묶음: { 지표 계산, 평가 시점, 단계 배열 [{n, rarity, reward}] }` 형태의 코드 상수. 단계를 추가·삭제해도 평가기 코드는 안 바뀐다.

#### 확장 묶음 — 승수 외 지표 (박스스코어 기반, 2026-10-31 추가)
데이터는 `game_pbp.home_box / away_box`(선수별 pts·reb·ast·stl·blk·tov·fgm·fga·p3m·p3a·ftm·fta·offReb·gs)와 `quarter_scores`(`{home:[Q1..Q4,OT], away:[...]}`)다. 3개 리그 전 경기에 존재함을 확인(NBA Active 496 / Pro Basketball League 1,321 / Test League 390행, 박스·타임라인·쿼터 점수 누락 0).
공통: 정규시즌만(플레이오프·올스타·트레이닝 제외), 팀 보유 이후 경기만, 결과 공개된 경기만.

**두 가지 보정 방식을 구분한다.**
- **순위형**(부문 순위, 개인 리더): 값이 아니라 리그 내 순위로 등급을 고정한다 → 엔진 튜닝으로 득점·스틸 환경이 바뀌어도 등급 비율이 유지된다.
- **횟수형**(130점+ 경기 수, 접전승 등): 절대값 임계라서 **엔진을 크게 바꾸면 분포가 이동**한다. 엔진 변경 후 달성률을 다시 집계해 임계값을 재보정해야 한다(보정 근거 표는 아래 "실측" 열).

- **증분 집계**: 매일 전체 시즌 박스(약 1,230행 × 선수 13명 JSONB, 시즌 약 4MB)를 다시 읽지 않는다. 그날 공개된 경기만 읽어 `(league_id, season_number, user_id)`별 카운터(jsonb)에 더하고, 마일스톤은 카운터로 판정한다. DB 반복 정지 조사(10-20) 이력상 시즌 전체 재스캔을 일일로 돌리는 건 피한다.

### ① 일일 정산 — 기본 소득 (2026-10-30 확정: 20/10 기준 + 점수차 변동)
**구현 2026-11-08** — `server/src/pointsSettlement.ts`(scheduler tick), 공식 `server/src/shared/points/dailySettlement.ts`, 워터마크 `rooms.points_settled_through`(기존 방 now() = 소급 없음). 원장은 **경기 1건 = 1행**(아래 "하루 1행" 설계와 다름 — 팀당 하루 최대 1경기라 동일). 공개 시각 이후·인수 이후 경기만.
- 하루 단위로 내 팀 경기 결과 정산. 승리 **20~25**, 패배 **5~10**.
- 점수차 `m = |내 점수 − 상대 점수|`, `t = min(5, floor(m / 4))` (점수차 20 이상이면 상한).
  - 승리: `20 + t` (신승 20 → 대승 25)
  - 패배: `10 − t` (석패 10 → 대패 5)
  - 같은 점수차면 승+패 합이 30으로 같아서, 5할 팀은 고정 20/10일 때와 같은 약 1,230P.
- 연장 경기는 점수차가 작아 자연히 신승·석패 구간. 올스타·플레이오프는 제외(정규시즌만).
- 원장 키 `daily:{league}:{season}:{date}:{user}` — 하루 1행으로 합산(`meta`에 경기별 점수차·금액 기록), 같은 날 두 번 정산돼도 1회.
- 시즌 합계 범위(82경기): 승/패 구성별 하한 = 20승 + 5패, 상한 = 25승 + 10패.

| 승-패 | 하한 | 상한 | 고정 20/10이었다면 |
|------|------|------|------|
| 30-52 | 860 | 1,270 | 1,120 |
| 41-41 | 1,025 | 1,435 | 1,230 |
| 50-32 | 1,160 | 1,570 | 1,320 |
| 60-22 | 1,310 | 1,720 | 1,420 |
| 82-0 | 1,640 | 2,050 | 1,640 |

- 실제 값은 점수차 분포에 따른다. 평균 승리 점수차 12·패배 12면 승 23 / 패 7로 5할 팀은 약 1,230P. 점수차가 크게 이기고 근소하게 지는 강팀일수록 위쪽으로 간다.
- 점수차 `4점당 1P`·상한 20점은 잠정. 시뮬 결과의 점수차 분포를 보고 조정.
