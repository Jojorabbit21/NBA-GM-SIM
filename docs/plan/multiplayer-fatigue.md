## 1. 현황 진단

### 1-1. 멀티에서 지금 실제로 일어나는 일

| 단계 | 싱글 | 멀티(서버) |
|---|---|---|
| 경기 중 소모·벤치/타임아웃/쿼터 회복 | ✅ | ✅ (같은 엔진) |
| 경기 종료 체력 이월 | ✅ `SavedPlayerState.condition` | ✅ `room_player_state.condition` (2026-09-03~) |
| **경기 사이 회복** | ✅ 유저 팀 비경기일에 리그 전원 +40 | ❌ **없음** |
| 백투백 소모 ×1.5 | 유저 경기만 | ❌ `false` 하드코딩 (`simRunner.ts:250-251`) |
| 훈련 중 부상 | ✅ 휴식일마다 굴림 | ❌ 없음 |
| UI 체력 표시 | ✅ | ❌ 멀티 화면엔 표시 없음 |

→ 체력이 회복 없이 경기마다 쌓여 내려가서, 주전과 벤치가 번갈아 탈진합니다.
- 실측 (Pro Basketball League, DET 주전): 경기 종료 체력이 10-21 84~89 → 10-23 46~59 → 10-25 경기 시작 직후 탈진
- 최근 30일 멀티 1,363경기에서 탈진 교체 4,396건 (경기당 3.2건)

### 1-2. 싱글 로직을 그대로 옮기면 안 되는 이유
- 싱글은 **유저 팀 일정 기준**으로 "오늘 유저 경기가 없으면 30팀 전원 +40"입니다. 그래서 CPU 팀은 실제 휴식과 무관하게 회복합니다. 멀티는 팀마다 일정이 다르므로 이 방식이 성립하지 않습니다.
- 멀티에는 매일 도는 "하루 틱"이 없습니다. 경기는 `scheduled_at`에 맞춰 개별적으로 시뮬됩니다. 그래서 회복은 **다음 경기를 시뮬할 때 경과일만큼 한꺼번에(lazy)** 계산하는 방식이 맞습니다.
- 싱글의 "하루 +40 고정"은 백투백 때 회복이 0이고, 하루만 쉬어도 사실상 만충입니다. 회복 결과가 극단적입니다.

### 1-3. 멀티 일정 특성 (Pro Basketball League 정규시즌, 팀별 연속 경기 간격)

| 간격(일) | 1 (백투백) | 2 | 3 | 4+ |
|---|---|---|---|---|
| 비율 | 12.9% | **76.5%** | 7.9% | 2.7% |

→ 대부분 "하루 쉬고 경기"입니다. 이 구간에서 정상 출전한 선수는 거의 회복되어야 하고, 백투백만 체감 페널티가 있어야 합니다.

## 2. 설계 원칙

1. **선수 단위·가상 날짜 기준**: 회복량은 "이 선수의 체력이 마지막으로 기록된 가상 날짜 → 이번 경기 가상 날짜"의 경과일로 계산합니다. 트레이드·FA 이적을 해도 계산이 그대로 성립합니다.
2. **lazy 계산**: 매일 배치 잡을 돌리지 않습니다. 경기 시뮬 직전과 UI 표시 시점에 같은 순수 함수로 계산합니다.
3. **악순환 차단, 관리 요소는 유지**: 무리하지 않은 출전은 하루 휴식으로 회복됩니다. 반면 혹사·백투백은 다음 경기까지 피로가 남습니다.
4. **client/server 미러**: 회복 함수는 `server/src/shared/engine/fatigueSystem.ts` ↔ `services/game/engine/fatigueSystem.ts`에 둡니다. UI 미리보기와 서버 판정이 같은 값을 내도록 하기 위함입니다.

## 3. 개선 내용

### 3-1. 데이터: `room_player_state.condition_date` 추가 (필수)
```sql
ALTER TABLE room_player_state ADD COLUMN condition_date date;  -- 이 condition이 기록된 가상 날짜(= 그 경기의 game_date)
```
- `simRunner` §6.5에서 체력을 upsert할 때 `condition_date = game.game_date`도 함께 기록합니다.
- `condition_date IS NULL`(기존 행이나 아직 경기를 안 뛴 선수)은 **완전 휴식(100)으로 간주**합니다.
- **기존 리그 정리 (결정 필요 D1)**: 이미 바닥으로 쌓인 체력을 그대로 둘지 결정해야 합니다. 권장은 1회성 리셋입니다. `UPDATE room_player_state SET condition = NULL` 또는 100으로 되돌립니다.

### 3-2. 경기 간 회복 공식 (핵심)

싱글의 고정 +40 대신 **부족분(100 − 체력)을 일정 비율로 줄이는 지수 회복**을 씁니다.

```
deficit       = 100 − condition
overnight     = deficit × OVERNIGHT_KEEP                  // 경기 다음날 아침까지
afterRest     = overnight × REST_DAY_KEEP^(days − 1)      // 경기 없는 날마다
keepModifier  = 1 − (stamina−50)/100 × 0.30 − (durability−50)/100 × 0.20   // 기존 RECOVERY_*_FACTOR 재사용
newCondition  = 100 − afterRest × keepModifier
```

| 상수 (제안) | 값 | 의미 |
|---|---|---|
| `OVERNIGHT_KEEP` | 0.5 | 경기 다음날까지 부족분의 50%가 남음 |
| `REST_DAY_KEEP` | 0.25 | 휴식일 하루마다 남은 부족분의 25%만 남음 |

`days`는 이번 경기 날짜에서 `condition_date`를 뺀 값입니다. 백투백이면 1입니다.

**예상 결과 (stamina·durability 50 기준)**

| 직전 경기 종료 체력 | 백투백 (days=1) | 하루 휴식 (days=2) | 이틀 휴식 (days=3) |
|---|---|---|---|
| 85 (주전 32~36분) | 92.5 | 98.1 | 99.5 |
| 70 (혹사 40분+ / 고페이스·프레스) | 85 | 96.3 | 99.1 |
| 50 (탈진 직전까지) | 75 | 93.8 | 98.4 |

- 정상 출전한 선수는 하루만 쉬면 98 이상으로 돌아오므로 악순환이 생기지 않습니다.
- 백투백은 다음 경기를 85~92로 시작하고, 거기에 3-3의 ×1.5 소모가 더해집니다. 그래서 4쿼터 체력과 탈진 위험이 체감될 정도로 커집니다.
- 지수 방식이라 100을 넘지 않습니다. 싱글처럼 "+40이면 무조건 만충"이 되지 않아 상수 튜닝 여지가 있습니다.
- 상수 2개는 `SIM_CONFIG.FATIGUE`에 추가합니다. 반영 전에 3-6의 시뮬로 값을 확정합니다(**결정 필요 D2**).

### 3-3. 백투백 판정 연결
- `simRunner`에서 팀별로 "같은 시즌에 이 팀이 치른 가장 최근 경기의 `game_date`"를 조회합니다. 이번 경기와 1일 차이면 `isHomeB2B`/`isAwayB2B`를 `true`로 넘깁니다(지금은 `false` 하드코딩).
- 선수 단위가 아니라 **팀 일정 기준**입니다. 실제 NBA의 B2B 개념과 같습니다. 이적한 선수는 새 팀 일정을 따릅니다.
- 쿼리 1회: `games`에서 `room_id`, 팀(홈 또는 원정), `played`, `game_date < 이번 경기 날짜`, `is_allstar`가 아닌 경기 중 `max(game_date)`.

### 3-4. 서버 적용 위치
`server/src/simRunner.ts`
- **§2.5 상태 오버레이**: `room_player_state`에서 `condition_date`도 함께 select합니다. 그 다음 `applyBetweenGameRecovery(condition, days, stamina, durability)` 결과를 `rosterState[pid].condition`에 넣습니다. 엔진(`buildTeamForSim` 이하)은 건드리지 않습니다.
- **§4 엔진 호출**: B2B 플래그 2개를 전달합니다.
- **§6.5 이월 upsert**: `condition_date: game.game_date`를 추가합니다.
- `postAllStarGame.ts`도 `room_player_state.condition`을 읽습니다(쓰지는 않음). 같은 회복 함수를 거치게 해서 표시와 판정을 일관되게 맞춥니다.

### 3-5. UI: 멀티 화면에 체력 노출 (권장, 2단계)
지금 멀티 유저는 체력을 볼 방법이 없어서 탈진을 관리할 수 없습니다.
- 로스터, 뎁스차트·로테이션 화면에 **"다음 경기 예상 체력"**을 표시합니다. 계산식은 `room_player_state.condition` + `condition_date` + 다음 경기 날짜를 같은 미러 함수에 넣는 것입니다. 날짜는 반드시 `current_virtual_date()`나 일정의 `game_date` 기준으로 잡습니다(`rooms.sim_date` 금지).
- 백투백 경기에는 일정·매치업 화면에 B2B 배지를 붙입니다.
- (선택) 선수별 휴식·복귀 임계치(`restThreshold`/`returnThreshold`)를 유저 전술 화면에도 엽니다. 지금은 어드민 `TeamTacticsTab`에서만 편집할 수 있습니다.

### 3-6. 검증 방법
- 2026-10-17 복귀 버그 검증에 쓴 재현 스크립트를 확장합니다(실제 로스터·전술로 서버 엔진을 실행). 한 팀의 실제 일정 20경기를 연속 시뮬하면서 회복 함수를 적용하고 다음 지표를 확인합니다.
  - 경기당 탈진 교체 수 (목표: 현재 3.2 → 1 미만, 백투백에서만 증가)
  - 주전 출전시간과 로테이션 차트 설정의 오차
  - 백투백 경기 vs 일반 경기의 주전 4쿼터 체력 차이
- 상수 2개(D2)를 바꿔가며 같은 일정으로 비교합니다.

## 4. 범위 밖 / 보류 제안

| 항목 | 보류 이유 |
|---|---|
| 훈련 중 부상 (휴식일 부상 굴림) | lazy 방식에서는 "지난 휴식일에 다쳤다"를 다음 경기 직전에 소급해 알게 됩니다. 뉴스·인박스 날짜와 이미 지나간 로테이션이 어긋납니다. 하루 틱이 생기거나 별도 설계가 필요합니다. |
| 시즌 누적 피로 (장기 혹사) | 경기 간 회복이 지수형이라 혹사 선수에게는 이미 잔여 피로가 남습니다. 효과를 보고 판단합니다. |
| 싱글 회복 로직 교체 | 싱글도 "유저 팀 기준 +40"이라는 왜곡이 있습니다. 같은 미러 함수로 통일할 수 있지만, 싱글 밸런스가 바뀌므로 별도 결정입니다(**결정 필요 D3**). |
| 아키타입 레이팅의 경기 중 체력 재계산 | 지금은 경기 시작 시 1회만 계산합니다. 멀티·싱글 공통 엔진 이슈라 별건으로 다룹니다. |

|---|---|---|
| D1 | 기존 리그의 쌓인 체력을 리셋할지 | **리셋** (`condition` NULL → 100 간주). 회복이 없던 기간의 피로는 버그로 생긴 것이라 보존할 이유가 없습니다. |

## 6. 작업 순서 (안)
1. 회복 함수 + 상수를 미러 쌍에 추가 (`fatigueSystem.ts` client/server)
2. DB 마이그레이션 `condition_date` + (D1) 리셋
3. `simRunner` §2.5 / §4 / §6.5, `postAllStarGame` 반영
4. 재현 스크립트로 시즌 구간 시뮬 → 상수 확정
5. Fly 배포 + dev-log 기록 (미러 쌍 모두)
6. (2단계) 멀티 UI 체력·B2B 표시
