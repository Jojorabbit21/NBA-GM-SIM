## 1. 현황 진단

### 1-1. 멀티에서 지금 실제로 일어나는 일

| 단계 | 싱글 | 멀티(서버) |
|---|---|---|
| 경기 중 소모·벤치/타임아웃/쿼터 회복 | ✅ | ✅ (같은 엔진) |
| 경기 종료 체력 이월 | ✅ `SavedPlayerState.condition` | ✅ `room_player_state.condition` (2026-09-03~) |
| **경기 사이 회복** | ✅ 유저 팀 비경기일에 리그 전원 +40 | ❌ **없음** |
| 백투백 소모 ×1.5 | 유저 경기만 | ❌ `false` 하드코딩 (`simRunner.ts:250-251`) |
| 훈련 중 부상 | ✅ 휴식일마다 굴림 | ❌ 없음 |
| UI 체력 표시 | ✅ | ❌ 멀티 화면엔 표시 없음 |

→ 체력이 회복 없이 경기마다 쌓여 내려가서, 주전과 벤치가 번갈아 탈진합니다.
- 실측 (Pro Basketball League, DET 주전): 경기 종료 체력이 10-21 84~89 → 10-23 46~59 → 10-25 경기 시작 직후 탈진
- 최근 30일 멀티 1,363경기에서 탈진 교체 4,396건 (경기당 3.2건)

### 1-2. 싱글 로직을 그대로 옮기지 않는 이유
- 싱글은 **유저 팀 일정 기준**으로 "오늘 유저 경기가 없으면 30팀 전원 +40"입니다. CPU 팀은 실제 휴식과 무관하게 회복합니다. 멀티는 팀마다 일정이 다르므로 선수 단위로 판단해야 합니다.
- "하루 +40 고정"은 백투백 때 회복이 0이고, 하루만 쉬어도 사실상 만충이라 결과가 극단적입니다.

### 1-3. 멀티의 가상 날짜 구조 (회복 시점을 잡는 근거)
`league_virtual_days`에 가상 날짜마다 실제 시각이 미리 정해져 있습니다. 서버는 날짜가 바뀌는 순간을 정확히 알 수 있습니다.

| 가상 날짜 (Pro Basketball League) | `real_start_at` | 경기 `scheduled_at` | `real_midnight_at` |
|---|---|---|---|
| 10-24 | 01:00:00 | 01:01 ~ 01:07 | 01:12:30 |
| 10-25 | 01:20:00 | 01:21 ~ 01:27 | 01:32:30 |

- 가상 하루가 실제 20분이고, 자정과 다음 날 첫 경기 사이에 약 7분 반의 여유가 있습니다.
- 경기는 `scheduled_at` 직전에 미리 시뮬되고(10-25 BKN@DET는 01:20:28에 시뮬), 결과는 리플레이가 끝난 뒤 공개됩니다.
- 현재 날짜 판정은 `current_virtual_date()`가 `real_midnight_at`을 기준으로 합니다. 회복도 같은 기준을 씁니다(`rooms.sim_date`는 사용 금지).

### 1-4. 멀티 일정 특성 (Pro Basketball League 정규시즌, 팀별 연속 경기 간격)

| 간격(일) | 1 (백투백) | 2 | 3 | 4+ |
|---|---|---|---|---|
| 비율 | 12.9% | **76.5%** | 7.9% | 2.7% |

→ 대부분 "하루 쉬고 경기"입니다. 이 구간에서 정상 출전한 선수는 거의 회복되어야 하고, 백투백만 체감 페널티가 있어야 합니다.

## 2. 설계 원칙

1. **DB 값 = 현재 체력**: `room_player_state.condition`은 항상 "지금 이 순간"의 체력입니다. 경기가 끝나면 깎이고, 자정이 지나면 회복됩니다. 읽는 쪽(엔진, 추후 UI)에서는 따로 계산하지 않습니다.
2. **선수 단위 판정**: 그날 경기를 뛰었는지는 "그 선수의 체력이 그날 경기로 기록됐는지"로 판정합니다. 트레이드·FA 이적과 무관하게 성립합니다.
3. **멱등성과 따라잡기**: 자정 회복은 방마다 "어디까지 처리했는지"를 기록해 두 번 적용되지 않게 합니다. 서버 다운 등으로 밀렸으면 다음 경기 시뮬 직전에 먼저 따라잡습니다.
4. **악순환 차단, 관리 요소는 유지**: 무리하지 않은 출전은 하루 휴식으로 회복됩니다. 반면 혹사·백투백은 다음 경기까지 피로가 남습니다.
5. **멀티 전용(D3)**: 회복 함수는 서버(`server/src/shared/`)에 두고 싱글 경로에서는 호출하지 않습니다. 다만 `SimSettings` 타입과 기본값은 client/server 미러 쌍이므로 둘 다 갱신합니다(설정 화면이 클라이언트에 있음).

## 3. 개선 내용

### 3-1. 데이터 변경

```sql
-- 이 condition에 자정 회복이 반영된 마지막 가상 날짜. 경기 종료 기록 시 game_date − 1
-- (경기는 그날 자정 전에 열리므로, 그날 자정 회복은 아직 반영 전)
ALTER TABLE room_player_state ADD COLUMN condition_recovered_through date;
-- 그 선수가 마지막으로 실제 출전(mp > 0)한 가상 날짜 — 자정 회복 시 "그날 뛰었나" 판정용
ALTER TABLE room_player_state ADD COLUMN last_game_date date;
-- 방별 자정 회복 처리 완료 지점 (스케줄러 효율용, 정합성은 행 단위 condition_recovered_through가 보장)
ALTER TABLE rooms ADD COLUMN fatigue_recovered_through date;
```

> **4단계에서 수정 (2026-10-17)**: 처음 계획은 `condition_date`(경기 종료 시 = D)였습니다. 그러면 "자정 D는 `condition_date < D`인 행만 회복"이라는 규칙에서 **그날 출전한 선수가 그날 자정 회복 대상에서 빠집니다.** 그래서 "자정 회복이 어디까지 반영됐는가"로 의미를 바꾸고, 경기 종료 시 D−1을 기록합니다.

- **조건부 갱신 RPC `apply_fatigue_recovery(p_room_id uuid, p_rows jsonb) returns int`** (5단계 마이그레이션에 포함)
  - `p_rows`: `[{ player_id, condition, recovered_through, expected_condition, expected_recovered_through }]`
  - 각 행을 `condition IS NOT DISTINCT FROM expected_condition AND condition_recovered_through IS NOT DISTINCT FROM expected_recovered_through`일 때만 갱신하고, 갱신된 행 수를 돌려줍니다.
  - 목적: 자정 회복이 행을 읽은 뒤 그 사이에 경기 종료 기록(simRunner)이 끼어들면, 회복으로 경기 결과를 덮어쓰지 않습니다. 건너뛴 행은 다음 자정이나 따라잡기에서 새 값 기준으로 다시 계산됩니다.
  - PostgREST 일괄 upsert는 행마다 조건을 걸 수 없어서 RPC로 만듭니다. `service_role` 전용입니다.
- **D1 리셋 (마이그레이션에 포함)**: `UPDATE room_player_state SET condition = NULL, condition_recovered_through = NULL, last_game_date = NULL;`
  - `condition IS NULL`은 엔진에서 100으로 간주합니다. 지금 `simRunner` §2.5가 이미 `row.condition != null`일 때만 덮어씁니다.
  - `rooms.fatigue_recovered_through`는 리셋 시점 기준 `current_virtual_date(room_id) - 1`로 채웁니다. 과거 날짜까지 소급 처리하지 않기 위해서입니다.
  - 부상·계약·부상 이력 칼럼은 건드리지 않습니다.
- `condition`은 있는데 `condition_recovered_through`가 NULL인 행은 기록 시점을 알 수 없는 값입니다(예: 마이그레이션과 서버 배포 사이에 구버전 서버가 쓴 값). 다음 회복 처리 때 **100으로 정리**합니다(D1과 같은 취지).

### 3-2. 경기 종료 시 (소모 기록) — `simRunner.ts` §6.5
- 지금처럼 경기 종료 체력을 upsert하면서 `condition_recovered_through = game.game_date − 1`을 함께 기록합니다(경기 직전 따라잡기로 이미 D−1까지 반영된 상태이므로 일치).
- `last_game_date = game.game_date`는 **실제 출전(mp > 0)한 선수에게만** 기록합니다. DNP 선수는 기존 `last_game_date`를 유지합니다.
- 기존 주석의 "upsert 행 구성을 섞지 말 것" 원칙에 맞춰, 출전자 upsert와 DNP upsert를 칼럼 구성별로 나눠 보냅니다.

### 3-3. 가상 자정 회복 (핵심) — 스케줄러 신규 단계

**트리거**: `scheduler.ts`의 30초 `tick()`에 단계를 추가합니다.
- 진행 중인 리그 방마다 `fatigue_recovered_through`보다 뒤이면서 `real_midnight_at <= now()`인 가상 날짜를 순서대로 처리합니다.
- 한 tick에서 여러 날이 밀려 있으면 날짜 순으로 전부 처리합니다(오프시즌, 서버 재시작 직후).

**처리 (`processRoomMidnights`, `server/src/fatigueRecovery.ts`)**
1. `real_midnight_at <= now`인 가장 최근 가상 날짜 D를 찾습니다. `rooms.fatigue_recovered_through >= D`면 아무것도 하지 않습니다.
2. 그 방의 `room_player_state` 중 `condition < 100`이고 `condition_recovered_through`가 NULL이거나 D보다 이전인 행을 읽습니다.
3. 선수마다 `condition_recovered_through + 1`부터 D까지 하루씩 회복을 적용합니다(밀린 날이 여러 개여도 한 번에). 그날이 `last_game_date`면 **경기 후 하룻밤 회복**, 아니면 **휴식일 회복**입니다.
4. `apply_fatigue_recovery` RPC로 조건부 반영하고(`condition_recovered_through = D`), 모든 행 처리가 끝난 뒤에만 `rooms.fatigue_recovered_through = D`로 전진합니다.
   - 중간에 실패하면 다음 tick이 같은 날짜를 다시 처리합니다. 이미 반영된 행은 2번 조건에서 빠지므로 이중 회복이 없습니다.

**회복 공식** (부족분을 비율로 줄이는 지수형):
```
deficit      = 100 − condition
keepRate     = (last_game_date = D) ? overnightKeep : restDayKeep
keepModifier = 1 − (stamina−50)/100 × 0.30 − (durability−50)/100 × 0.20   // 기존 RECOVERY_*_FACTOR 재사용
newCondition = 100 − deficit × keepRate × keepModifier
```

| 설정 키 (`sim_settings`) | 시작값 | 의미 | 조정 범위 (안) |
|---|---|---|---|
| `fatigueOvernightKeep` | 0.5 (확정) | 경기를 뛴 날 자정에 부족분이 이 비율만큼 남음 | 0.3 ~ 0.7 |
| `fatigueRestDayKeep` | 0.25 (확정) | 경기 없는 날 자정에 부족분이 이 비율만큼 남음 | 0.1 ~ 0.5 |

- "그날 경기를 뛰었다"(`last_game_date = D`)는 **실제 출전(mp > 0)한 선수만** 해당합니다. `rosterUpdates`에는 DNP 선수까지 모두 담기므로, §6.5에서 `last_game_date`는 박스스코어 출전자에게만 기록합니다. 시뮬도 이 기준으로 돌렸습니다.

**예상 결과 (시작값, stamina·durability 50 기준)** — 직전 경기 날 자정 1회 + 휴식일 자정 (n−1)회를 거친 다음 경기 시작 체력:

| 직전 경기 종료 체력 | 백투백 | 하루 휴식 | 이틀 휴식 |
|---|---|---|---|
| 85 (주전 32~36분) | 92.5 | 98.1 | 99.5 |
| 70 (혹사 40분+ / 고페이스·프레스) | 85 | 96.3 | 99.1 |
| 50 (탈진 직전까지) | 75 | 93.8 | 98.4 |

- 시작값은 추정치입니다. **3-7 시뮬로 기본값을 확정**합니다(D2).
- 능력치 조회: 일반 방은 `meta_players.base_attributes`(`custom_overrides` 적용 여부는 `shouldUseCustomOverrides`와 동일하게 처리)를 씁니다. 개인 팩 드래프트 방은 `room_player_instances` → `meta_player_cards`(없으면 `meta_players`)로 찾습니다. simRunner의 기존 매핑을 공용 헬퍼로 빼서 같이 씁니다.

### 3-4. 경기 시뮬 직전 따라잡기 (안전장치) — `simRunner.ts` §2.5 앞
- 스케줄러가 주된 경로이고, simRunner는 놓친 것을 보충하는 역할입니다.
- simRunner는 시뮬 전에 항상 `recoverPlayersThrough(roomId, game_date − 1, { playerIds: 양 팀 로스터 })`를 호출합니다. 이미 반영된 선수는 조회 조건에서 빠지므로, 스케줄러가 제때 처리했다면 아무 일도 하지 않습니다.
- 필요한 경우: 서버 재시작, 스케줄러 지연, 관리자 강제 시작(`forceStartNow`) 등으로 전날 자정 처리 전에 경기가 시뮬되는 상황.
- 같은 날짜를 스케줄러와 시뮬러가 동시에 처리해도 행 단위 `condition_recovered_through` 조건과 조건부 RPC 덕분에 이중 적용이 없습니다.

**타임라인이 없는 방 (D7)**
- 토너먼트(브래킷) 모드와 타임라인 도입 이전의 구 리그는 `league_virtual_days`가 없습니다(`finalize.ts`의 `bracketData` 분기, `timelineStore.ts` 주석). 그래서 스케줄러가 처리할 자정이 없습니다.
- 반면 경기 후 체력 이월(§6.5)은 모드와 관계없이 돌므로, 지금 이 방들도 체력이 쌓여 내려가는 상태입니다.
- 처리: 위 따라잡기가 **타임라인 행이 아니라 날짜 계산**으로 돕니다. 선수마다 `condition_recovered_through + 1`부터 `game.game_date − 1`까지 하루씩 세면서 같은 회복 함수(`recoverThrough`)를 적용합니다. 리그 모드에서 스케줄러가 하는 계산과 같은 함수입니다.
- 스케줄러 자정 회복(`processRoomMidnights`)은 타임라인이 없으면 아무것도 하지 않습니다.
- 타임라인이 없는 방은 `rooms.fatigue_recovered_through`를 쓰지 않고 선수 행의 `condition_recovered_through`만으로 판정합니다. 리그 모드에서도 이 행 단위 값이 최종 방어선이므로 두 경로가 같은 규칙을 공유합니다.

### 3-5. 백투백 판정 연결 — `simRunner.ts` §4
- 팀별로 "이 팀이 치른 가장 최근 경기의 `game_date`"를 조회합니다. 이번 경기와 1일 차이면 `isHomeB2B`/`isAwayB2B`를 `true`로 넘깁니다(지금은 `false` 하드코딩).

**백투백 소모 배율 설정화 (D6)** — 엔진 수정 (client/server 미러 쌍)
