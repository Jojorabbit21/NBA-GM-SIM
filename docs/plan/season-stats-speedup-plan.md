# 시즌 기록 조회 가속 — 두 방식 비교

작성: 2026-11-12 · 상태: **방식 B · 트리거 확정(사용자 결정 2026-11-12), 슛 위치 표는 나중에** — **1단계 적용 완료(2026-11-12 밤, 아래 12절)** — 표·트리거가 운영 DB에 있고 기존 경기를 채웠다. 조회·화면은 아직 그대로(2단계 대기). 선행 작업인 서버 저장 실패 확인·재시도는 배포 완료(Fly v243).

## 1. 배경

- 선수 프로필 퍼센타일 탭을 손보다가 선수 시즌 기록 조회 한 번이 DB에서 평균 2.2초 걸린다는 것을 확인했다.
- 10월의 DB 반복 정지 때 "미리 계산해 두는 방식"을 미뤄 둔 상태였다(인스턴스 사양을 올려 넘김).
- 사용자가 정한 것:
  - 기록은 **경기 스포일러 방지가 끝나는 시각(공개 시각)마다** 갱신되어 보인다.
  - 켜 놓은 화면도 자동으로 갱신된다. 리더보드의 **새로고침 버튼은 없앤다**.
  - 설계 전에 무거운 조회를 전부 밝힌다(아래 2절).

## 2. 무거운 조회 (2026-11-05 ~ 11-12, 7.0일)

DB 전체 실행 시간 373분 대비 비중. 진행 중인 방은 한두 개였다.

| 순위 | 조회 | 식별자 | 쓰는 화면 | 호출 | 1회 평균 | 비중 |
|---|---|---|---|---|---|---|
| 1 | 실시간 알림용 변경 감시 | `realtime.list_changes` (Supabase 내부) | 앱 전체 | 95만 | 0.008초 | 32.2% |

| 3 | 팀 시즌 기록 | `get_team_season_advanced_stats` | 리더보드, 전술, 퍼센타일 | 3,623 | 0.48초 | 7.7% |

- **2~7번의 원인은 같다.** 방의 모든 경기 기록(JSON)을 요청이 올 때마다 처음부터 훑는다. 선수 한 명의 기록을 볼 때도 1,300경기를 전부 읽는다.
- 2번은 임시 파일도 7일간 163GB를 썼다(요청당 약 54MB).
- 6번은 압축 5.2MB, 풀면 49MB를 내려받는다(실측). 선수 한 명의 경기 로그를 위해 방 전체를 받는다.
- 8번은 데이터는 이미 정리된 표인데 접근 권한을 행마다 확인해서 느리다.
- 4·6·7·8번은 코드에서 다시 받는 계기를 찾지 못했다. 접속 중에는 갱신되지 않는 것으로 보인다(화면 미확인).
- 유저 요청의 제한 시간은 8초이고, 2번의 최대 기록이 7.5초였다.

## 3. 방식 A — 계산 결과를 저장하고 예약 작업으로 갱신

- 선수 시즌 기록과 팀 시즌 기록의 **계산 결과**를 방별·정규/플레이오프별로 표에 저장한다.
- DB 안의 예약 작업(pg_cron)이 10초쯤마다 진행 중인 방을 차례로 보고, 공개된 경기 수가 바뀐 방만 지금 계산식 그대로 다시 계산해 교체한다.
- 기존 조회는 이름을 그대로 두고 저장분을 읽는다. 저장분이 없거나 오래 밀리면 지금 방식으로 직접 계산한다.
- 브라우저는 "새 기록이 준비됐다"는 실시간 신호를 받아 다시 받는다.
- 해결 범위: 2·3번. 7번은 같은 방식으로 추가할 수 있다. 4·5·6번은 선수마다 결과가 달라 이 방식에 맞지 않는다.

## 4. 방식 B — 경기 기록을 "경기별·선수별 한 줄"로 풀어 저장

- 경기 기록이 저장될 때 박스스코어 JSON을 **선수 한 명당 한 줄**로 풀어 일반 표에 같이 넣는다(DB 트리거). 기존 경기는 한 번에 채운다.
- 조회는 이름을 그대로 두고 이 표를 읽는다. 선수 한 명의 기록은 약 90줄, 방 전체 합계는 약 3만 줄을 읽는다.
- 예약 작업이 없다. 공개 시각이 지난 줄만 읽으므로 공개되는 순간 바로 맞는 값이 나온다.
- 슛 위치 기록(4번)은 같은 방식으로 선수·경기별 표를 하나 더 둔다.
- 해결 범위: 2~7번.

## 6. 권장: B

- **범위가 넓다.** 같은 원인을 가진 여섯 조회가 한 번에 풀린다. 선수 프로필과 전술 화면처럼 A로는 그대로 남는 화면이 빨라진다.
- **A가 풀려던 문제도 풀린다.** 선수 기록 계산이 17ms라서, 요청마다 계산해도 접속자가 몰릴 때 문제가 되지 않는다. 저장분, 예약 작업, 준비 신호가 필요 없다.
- **멈춰도 낡은 값이 나오지 않는다.** A는 예약 작업이 멈추면 기록이 조용히 낡는다. B는 읽을 때 공개 시각을 따지므로 지연이 없다.

B에서 받아들여야 하는 것:

- **경기 저장 경로에 트리거가 붙는다.** 트리거가 잘못되면 경기 저장이 느려지거나 실패할 수 있다. 트리거 안의 오류가 경기 저장을 막지 않게 만들고, 빠진 줄이 없는지 대조하는 점검을 둔다.
- **같은 데이터가 두 군데 있다.** 원본은 지금의 JSON이고 표는 사본이다. 사본이 어긋나면 원본에서 다시 채울 수 있다.
- **새 기록 항목을 추가할 때 고칠 곳이 늘어난다.** 엔진이 박스스코어에 항목을 더하면 표의 열, 트리거, 조회를 같이 고쳐야 한다.

A는 버리는 것이 아니라 뒤로 미룬다. 방이 수십 개로 늘어 17ms짜리 계산도 부담이 되면 그때 B 위에 얹는다. 그때는 재계산도 싸다.

## 7. B 적용 단계

각 단계는 따로 되돌릴 수 있다.

| 단계 | 내용 | 유저에게 보이는 변화 |
|---|---|---|
| 1 | 표와 트리거를 만들고 기존 경기를 채움. 조회는 그대로 | 없음. 표에서 낸 합계가 지금 조회 결과와 같은지 방마다 대조하고, 실제 경기 하루를 지켜봄 |
| 2 | 조회를 하나씩 새 표를 읽게 교체 (2번부터) | 기록 조회가 빨라짐 |
| 3 | 브라우저: 선수 경기 로그를 선수 한 명분만 받게 교체, 공개 시각마다 자동 갱신, 새로고침 버튼 제거 | 프로필이 가벼워지고 켜 놓은 화면이 갱신됨 |
| 4 (선택) | 슛 위치 표(4번), 팀 플레이타입 조회의 권한 확인 방식(8번) | 슛 차트, 전술 화면이 빨라짐 |

## 8. 위험과 대비

### 유저에게 큰 불편이 될 수 있는 경우 (2가지)

**① 트리거 때문에 경기 기록 저장이 실패하는 경우 (1단계)**
- 서버는 경기 기록 저장(`server/src/simRunner.ts` 의 `game_pbp` upsert)이 성공했는지 확인하지 않고 다음으로 넘어간다. 저장이 실패해도 그 경기는 "끝난 경기"로 표시되고 점수가 남는다.
- 그러면 점수는 있는데 중계·박스스코어·기록이 없는 경기가 조용히 생긴다. 다시 시뮬하지 않는 한 복구되지 않는다.
- 대비:
  - 트리거 본문 전체를 오류 처리로 감싼다. 트리거 안에서 무슨 오류가 나도 기록만 남기고 경기 저장은 그대로 진행한다.
  - 트리거가 표 잠금을 0.2초 넘게 기다리지 않게 한다(넘으면 그 경기는 건너뛰고 나중에 채움). 잠금 대기로 저장 요청이 제한 시간에 걸리는 것을 막는다.
  - 새 표의 구조 변경은 경기가 도는 시간대를 피해서 한다.
  - 1단계에서 실제 경기 하루를 지켜보며 "저장된 경기 수 = 표에 들어온 경기 수"를 확인한다.
- **(2026-11-12 반영)** 서버가 저장 결과를 확인하도록 고쳤다 — 실패 시 2회 재시도, 그래도 실패하면 끝난 경기로 표시하지 않고 다음 30초 주기에 다시 시뮬한다(`server/src/saveWithRetry.ts`, 커밋 e16ab465·Fly v243). 이제 트리거가 저장을 실패시키더라도 기록 없는 경기가 조용히 생기지는 않고, 그 경기가 시작되지 않은 채 반복 시도된다. 아래 대비는 여전히 필요하다.
- 트리거를 아예 쓰지 않는 대안: 조회가 읽기 직전에 "표에 아직 없는 경기"를 채운다. 경기 저장 경로를 건드리지 않는다. 대신 이미 저장된 경기를 다시 시뮬해 덮어쓰는 경우(관리자 수동 시뮬)를 따로 처리해야 한다.

**② 교체한 조회가 오류를 내는 경우 (2단계, 방식 A도 같음)**
- 리그 진입 화면은 선수 시즌 기록 조회가 끝나야 넘어간다(`hooks/useLeagueBootstrap.ts`). 이 조회가 계속 실패하면 전원이 리그에 들어오지 못한다.
- 대비:
  - 새 조회를 다른 이름으로 먼저 만들어 기존 조회와 결과를 전수 대조하고, 실제 유저 권한 경로에서 속도를 잰다.
  - 교체한 조회 안에 안전장치를 둔다. 새 표를 읽다 오류가 나거나, 표의 경기 수가 원본과 다르면 지금 방식으로 계산해 돌려준다. 최악의 경우가 지금과 같다(느리지만 맞는 값).
  - 기존 조회 본문을 보관해 두고, 교체는 경기가 없는 시간대에 한다. 되돌리기는 함수 본문 하나를 바꾸는 일이다.

### 그 밖의 위험


| 위험 | 대비 |
|---|---|
| 표에 빠진 경기 (기록이 한 경기 적게 나옴) | 조회가 표의 경기 수와 원본 경기 수를 비교하고, 다르면 지금 방식으로 계산. 빠진 경기는 원본에서 다시 채움 |
| 경기 삭제·리그 초기화 뒤 표에 남은 줄 | 원본 경기가 지워지면 표의 줄도 같이 지워지게 연결 |
| 스포일러 누출 | 표에 경기 시작 시각과 연장 횟수를 같이 두고, 조회가 공개 시각 식(`game_reveal_at` 과 같은 식)으로 걸러 읽음. 표 접근 규칙은 경기 기록과 같게(방 멤버·관전자) |
| 리플레이 길이 설정이 시즌 중 바뀜 | 공개 시각을 표에 값으로 박지 않고 읽을 때 계산 |
| 값이 달라짐 | 계산식을 바꾸지 않음. 2단계 전후로 조회 결과를 전수 대조 |
| 예전 버전 화면 | 조회 이름과 인자를 그대로 두므로 그대로 동작 |

## 9. 미확인

- 실제 표(접근 권한 검사 포함)에서의 속도. 1단계에서 잰다.
- 팀 시즌 기록(3번)은 경기별 팀 부가 기록(속공 득점 등)을 경기 기록에서 같이 읽어야 한다. 그 부분의 비용.
- 로스터의 기록·일정 탭이 방 전체 박스스코어에서 무엇을 쓰는지. 3단계에서 본다.
- 올스타·연습 경기·토너먼트 방의 처리(지금 조회는 올스타를 제외한다).
- 1번(실시간 변경 감시 32%)은 무엇이 비용을 키우는지 분석하지 않았다. 이 계획의 범위 밖이다.
- 선수 뉴스 조회(평균 1.0초, 호출 적음)도 범위 밖이다.

### 사전 점검 결과 (2026-11-12)

운영 DB에서 한 트랜잭션으로 전부 만들고, 시험한 뒤, 전부 되돌렸다(남은 것 없음 확인). `Test League` 1,294경기 기준.

| 점검 | 결과 |
|---|---|
| 열 68개가 지금 조회 함수의 정의와 일치 | 일치 |
| 기존 경기 채우기 | 1,294경기 → 헤더 1,294줄, 선수 38,760줄, 17.4초 (경기당 약 13ms) |
| 크기 | 헤더 0.8MB + 선수 14.9MB |
| 한 경기에 같은 선수가 두 번 | 0건 |
| 합계가 지금 조회와 같은가 (정규시즌 / 플레이오프 / 합산) | 세 경우 모두 차이 0줄 (450 / 265 / 450명) |
| 경기 기록 수정 시 트리거 | 그 경기 30줄이 다시 채워짐 |
| 깨진 박스스코어를 저장 | 저장은 성공, 그 경기는 표에서 빠짐, 잠금 대기 설정 원복 |
| 경기 기록 삭제 | 표의 줄도 같이 삭제 |

- **트리거 비용은 경기 한 건당 약 13ms**다. 처음 예상(수 ms)보다 크지만 경기 저장 한 번에 한 번이라 영향은 없다.
- **조회 속도에 대해 새로 알게 된 것**: 표를 단순하게 읽으면 선수 시즌 기록이 458ms였다(지금 1,675ms). 공개 시각을 경기마다 함수로 계산하는 비용(1,294번, 약 0.3ms씩)이 대부분이다. 4절의 17ms는 공개 시각을 미리 계산해 둔 상태로 잰 값이다. 2단계 조회는 리플레이 길이를 한 번만 읽어 공개 시각을 계산하게 만들고, 1단계 적용 뒤 실제 표에서 다시 잰다.
- 나머지 두 방(`NBA Active`, `Pro Basketball League`)의 합계 대조는 적용 뒤 방마다 한다(적용 절차의 일부).

### 적용 절차

1. 표·함수·트리거 생성 (수 ms. 경기 기록 표에 아주 짧은 잠금)
2. 방별로 기존 경기 채우기 (방당 약 17초, 경기 저장을 막지 않음)
3. 방 3개 × 정규/플레이오프/합산 합계 대조, 경기 수 대조
4. 다음 실제 경기(`Test League` 낮 12:00)에서 새 경기가 표에 들어오는지, 서버 로그에 저장 재시도가 없는지 확인

되돌리기: 트리거 → 함수 2개 → 표 2개 순으로 삭제. 기존 동작에는 영향이 없다.
