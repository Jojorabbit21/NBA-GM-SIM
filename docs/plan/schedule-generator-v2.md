## 1. 배경

Pro Basketball League 일정을 실제 NBA와 비교해 보니 아래 문제가 있었다(2026-10-22 조사, 연구 문서 §1).

- 마지막 날 1경기, 6팀만 그날 시즌 종료. 4월 일정이 몇 경기씩 늘어지며 끝남.
- 하루 경기 수가 9·6·9·6으로 교대로 반복되고 요일 리듬이 없음. 개막일 9경기.
- 팀당 B2B가 6~15회로 편차가 큼. 4-in-5가 51건.
- 추수감사절에 경기가 있음. 같은 경기장 2연전이 거의 없음.

원인은 `assignDates`가 매치업을 셔플한 뒤 날짜를 앞에서부터 그리디로 채우는 구조다. 하한 제약(B2B 하한, 마지막 날 전원 경기)은 이 방식으로 지킬 수 없다.

현행(10/21~4/13 고정, 175일)과 길이가 하루 차이라 타임라인 실현 가능성 계산에는 거의 영향이 없다.

### 3.1 올스타 브레이크 배치 (결정 A 필요)

현행 브레이크는 6일이고, 날마다 성격(kind)이 하나씩 붙어 있다: `allstar_announce`(1일차) → `allstar_rising`(2) → `allstar_contests`(3) → `allstar_main`(4) → `allstar_break`(5~6). 현재 코드에서 하루의 kind는 하나뿐이고, 브레이크 기간에는 정규시즌 경기를 넣지 않는다.

실제 NBA: 목요일 경기 → 금(라이징스타) · 토(컨테스트) · 일(본경기) → 월·화·수 휴식 → 목요일 재개(10시즌 중 9시즌).

| 안 | 배치 | 경기 없는 날 | 장단점 |
|---|---|---|---|
| **A (권장)** | 목 발표 · 금 라이징 · 토 컨테스트 · 일 본경기 · 월화 휴식 → **수요일 재개** | 6일(목~화) | kind 의미·6일 길이 그대로라 기존 코드 변경 최소. 실제와는 하루씩 앞당겨짐(2024-25 실제는 수요일 재개라 그 시즌과 같음) |
| B | 목 **경기 + 발표** · 금~일 행사 · 월~수 휴식 → 목요일 재개 | 6일(금~수) | 실제와 같음. 단 "발표일에도 정규 경기가 있는 날"을 허용해야 해서 달력 구성·날짜 스트립·스케줄러 발표 트리거를 다시 확인해야 함 |

연동 날짜는 모두 브레이크 시작일 기준 상대값이라 자동으로 따라간다: 선발 확정 = 시작 −7일, 투표 = 그 전 28일, 중간 발표 3회.

트레이드 데드라인 기본값(2월 둘째 목요일, `utils/tradeDeadline.ts`)은 올스타와 별개로 계산된다. 2026-27 기준으로 데드라인 2/11(목)이 안 A의 발표일과 같은 날이 되지만, 두 이벤트가 충돌하지는 않는다. 바꾸지 않는다.

## 4. 저장·호환 설계

### 4.1 문제
`getAllStarKeyDates(virtualSeasonYear)`는 연도만으로 날짜를 계산하는 순수 함수이고, 클라이언트·서버 18개 파일 30곳에서 호출한다. 진행 중인 리그 2개(Pro Basketball League, AS 2)는 둘 다 가상 연도가 2026이고, 새 리그도 생성 시점 연도(2026)를 쓴다. **연도만으로는 구 규칙과 신 규칙을 구분할 수 없으므로**, 함수 안의 규칙을 바꾸면 진행 중인 리그의 올스타 날짜가 이동해 깨진다.

### 4.2 해법: 리그별 달력 저장
- 새 컬럼 **`leagues.season_calendar jsonb`** (null = 구 규칙 리그):
  ```json
  { "version": 2,
    "regularStart": "2026-10-20", "regularEnd": "2027-04-11",
    "allStar": { "start": "2027-02-11", "end": "2027-02-16",
                 "risingStars": "2027-02-12", "contests": "2027-02-13", "mainGame": "2027-02-14" } }
  ```
- 새 순수 모듈 **`seasonCalendar.ts`** (클라이언트 `utils/` ↔ 서버 `server/src/shared/` 미러):
  - `buildSeasonCalendar(virtualSeasonYear)` → 위 객체 (§3 규칙)
  - `legacySeasonCalendar(virtualSeasonYear)` → 현행 고정값(10/21~4/13, 2/13~18)
  - `resolveSeasonCalendar(league)` → `league.season_calendar ?? legacySeasonCalendar(year)`
- `getAllStarKeyDates(year, calendar?)`: calendar가 있으면 그 날짜를 기준으로 파생값(투표·선발·중간 발표)을 계산하고, 없으면 현행과 동일하게 동작한다. **진행 중 리그는 동작이 바뀌지 않는다.**
- 호출부 30곳은 `league.season_calendar`를 함께 넘기도록 바꾼다(기계적 변경). 서버 쪽 `leagues` 조회 select에 컬럼을 추가한다.
- 리그 생성 전(`CreateLeagueModal`, 실현 가능성 계산)에는 저장값이 없으므로 `buildSeasonCalendar(year)`를 직접 쓴다. 생성기도 같은 함수를 쓰므로 둘이 어긋나지 않는다.
- `finalize.ts`: `buildSeasonCalendar` → 일정 생성 → 타임라인(`buildVirtualCalendar`가 calendar를 받음) → `leagues.season_calendar` 저장. 이 순서로 올스타 일정이 정규시즌 일정과 **한 번에** 만들어진다.

> 대안으로 `schedule_rules_version int`만 저장하는 방식도 가능하다. 다만 생성기가 날짜를 정하는 구조(결정 3)와 맞지 않고, 이후 규칙을 또 바꾸면 같은 문제가 반복되므로 날짜 자체를 저장하는 방식을 권장한다.

## 5. 생성 알고리즘

입력: 30팀 정보, `SeasonCalendar`, 시드. 출력: `Game[]`(형식은 현행과 같다).

### 5.1 단계

1. **매치업 생성** — 현행 `generateMatchups` + `balanceHomeAway` 유지(4/4/3/2 공식은 실측과 이미 같다).
2. **2연전 묶기** — 같은 홈에서 2경기 이상 열리는 상대 쌍(디비전 4경기·컨퍼런스 4경기 쌍, 컨퍼런스 3경기 쌍의 2홈 쪽) 중 약 37쌍을 시드로 뽑아 **2경기짜리 한 단위**로 묶는다.
   - 실측: 컨퍼런스 4경기 쌍 57%, 컨퍼런스 3경기 쌍 22%, 디비전 20%. 간격은 이틀(하루 쉬고 다시) 84%, 연속일 15%.
   - 팀당 시즌 0~5회(평균 약 2.5회). 4월에는 드물다.
3. **날짜 틀** — 날짜마다 목표 경기 수와 고정 사항을 정한다.
   - 요일 가중치: 월 14.9 / 화 11.0 / 수 18.3 / 목 10.5 / 금 17.5 / 토 13.6 / 일 14.1(%).
   - 개막 1일차 2경기, 2일차까지 30팀 전원 첫 경기. 개막 주간 B2B 금지.
   - 추수감사절·크리스마스 이브 0경기. 크리스마스 5경기, 출전 팀은 앞뒤 B2B 금지.
   - 마지막 주: 금 15경기(30팀) · 토 0경기 · 일 15경기(30팀).
   - 올스타 브레이크(§3.1)는 0경기.
4. **예약 배치** — 마지막 일요일과 금요일에 쓸 "30팀이 한 번씩 나오는 15경기 조합" 2개를 남은 매치업에서 겹치지 않게 뽑아 고정한다. 크리스마스 5경기, 개막일 2경기도 먼저 고정한다.
5. **초기 배치** — 현행 그리디와 비슷하게 채우되 날짜 틀의 목표 경기 수를 따른다. 2연전은 한 단위로 넣는다. 하드 제약을 적용한다.
6. **다듬기(국소 탐색)** — 경기(또는 2연전 단위)를 다른 날로 옮기거나 두 경기의 날짜를 맞바꾼다. 하드 제약을 어기는 이동은 거부하고, 벌점 합이 줄면 받아들인다(필요하면 담금질 방식으로 가끔 나빠지는 이동도 허용). 시드 기반 RNG라 결정론이 유지된다.
7. **경기 시각** — 현행 `assignGameTimes` 유지.
   - [2026-10-26] 이후 `enforceB2BGaps`로 B2B 간격 보정: 같은 팀 B2B 두 경기의 실제 간격이 리그 설정 전 조합에서 "리플레이 + 연장 2회 + 여유 2분" 이상이 되도록 시각만 옮김(날짜 불변). 판정 `leagueTimeline.isB2BGapSafe`. 배경 `docs/plan/overtime-system.md` 2-6

### 5.2 하드 제약
- 한 팀 하루 2경기 금지, 3-in-3 금지, **4-in-5 금지**
- 고정 날짜(개막일·크리스마스·추수감사절·이브·마지막 금토일·올스타)는 이동 불가
- 크리스마스 출전 팀의 앞뒤 B2B 금지, 개막 주간 B2B 금지
- [2026-10-26] B2B 경기 시각 쌍 `isB2BGapSafe` 위반 금지(첫날 늦은 경기 + 둘째 날 이른 경기 조합 차단) — 날짜 배정 후 시각 단계에서 보장

### 5.3 벌점 항목 (이동 거리 관련 항목은 결정 1에 따라 제외)

| 항목 | 목표 (실측, 현재 시대) |
|---|---|
| 팀당 B2B | 12~17, 목표 14~15. 범위 밖은 큰 벌점 |
| 5-in-7 | 팀당 3 이하 |
| 휴식일 분포 | 0일 18% / 1일 64% / 2일 15% / 3일+ 3% |
| 휴식 불균형(B2B 팀 vs 2일+ 쉰 팀) | 전체의 7% 이하 |
| 연속 원정/홈 길이 | 8 이하. 5+ 연전 팀당 1~2회. 1경기짜리 비율 약 40% |
| 같은 상대 재대결 | 2연전 외에는 7일 이상 간격 |
| 날짜별 경기 수 | 날짜 틀 목표와의 차이 |
| 최장 휴식(올스타 제외) | 5일 이하 |
| 전반 41경기 홈 수 | 17~24 |

연속 원정 길이·1경기짜리 비율은 이동 거리와 별개인 "홈/원정 흐름" 지표라 남긴다.

### 5.4 성능
1,230경기·팀 30개라 이동 하나의 벌점 변화는 관련 팀 2~4개만 다시 계산하면 된다(증분 계산). 서버(Bun) 기준 수만~수십만 회 반복을 수 초 안에 끝내는 것을 목표로 한다. 리그 생성 시 한 번만 실행된다.
